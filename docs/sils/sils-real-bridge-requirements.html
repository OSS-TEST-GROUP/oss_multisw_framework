실 브리지 요구사항 — MORAI · Autoware 연동

SiLS vECU를 실제 MORAI(플랜트) + Autoware(인지·판단)와 닫힌 루프로 연동하기 위한 요구사항. 정규 계약·vECU·판정·요구/시나리오는 이미 완성 — 남은 일은 "알려진 ROS2 메시지 ↔ 알려진 정규 계약" 번역 + 기동 배관이다. 브리지 두 개가 몸통, 어디에도 안 속하는 공통층(clock·interop·오케스트레이션)이 소수.

MORAI · 상태(외부) 타깃 · 브리지 · MMF 우리 SiLS · 명령 #1 구축 대상 (미완)

0 · 토폴로지 — 데이터 평면 + 제어 평면(MMF)

세 구역: 외부(MORAI·Autoware) / 브리지(#1, 구축 대상) / 우리 SiLS(완료). "우리 SiLS"는 vECU만이 아니라 ClockMaster·conformance 판정·.xosc importer를 포함한다.

권위(authority) = MORAI(공유 세계). 브리지는 ROS2 ↔ 우리 DDS 정규 계약 경계(rclcpp 노드). ClockMaster tick에 MORAI가 물리는지가 결정론을 좌우(BR-C-1). MMF는 배포·수명 관리 평면(데이터 루프 아님).

1 · 이미 확정된 것 — 브리지 개발자가 건드리지 않는 경계

자산위치상태

vECU(VCU) 소비/발행service/sils/vecu · 예제 vehicle-interface✅ 상태+타깃 소비 → 통합 명령 발행

판정 트레이스vECU가 state_received / target_received / control_published emit✅ 버스에 실 데이터만 얹으면 자동 판정

브리지의 유일한 책임 = "실 데이터를 정규 토픽에 얹기". 트레이스 캡처·판정은 공짜로 따라온다.

형태: rclcpp 노드. MORAI ROS2 토픽 ↔ 우리 DDS 정규 토픽 양방향 번역.

3 · [BR-A] Autoware 연동 브리지

형태: rclcpp 노드. Autoware 제어 출력 → 정규 ControlTarget. 단위가 우리와 거의 일치해 가장 쉽다.

BR-A-1

타깃 IN  ·  Autoware 제어 → ControlTarget @ autoware/control_target

정규 ControlTargetAutoware 소스변환
steering_angle (rad)Control.lateral.steering_tire_angle (rad)1:1
acceleration (m/s²)Control.longitudinal.acceleration (m/s²)1:1
gear (0~3)GearCommand (DRIVE=2 / REVERSE=20 / PARK=22 / NEUTRAL=1)enum 매핑 (DRIVE→3·REV→1·PARK→0·NEU→2)

control_cmd(제어)와 gear_cmd(기어)는 별도 토픽 → 최신값 병합해 한 ControlTarget으로. staging은 vECU가 §7.3로 처리.

BR-A-2 · 차량 상태 피드백: Autoware는 계획을 위해 /vehicle/status/*를 입력받아야 한다(소스=MORAI). 결정 필요: MORAI→Autoware 직접(ROS2) vs 상태 브리지가 EgoState 역변환.

4 · [BR-C] 공통층 (둘 다 아니지만 필수)

BR-C-1

시간 동기 (clock) — 최우선 리스크

[확인] MORAI가 외부 스텝/동기 제어(네트워크 sync·step API)를 지원하는가?

지원 O → MORAI를 ClockMaster barrier 참가자로 → 실 루프도 L3 bit-재현 결정론 유지.
지원 X → MORAI wall-free-run → 실 루프는 "동작 검증"(루프 닫힘·안전)까지, 결정론은 포기(evaluate wall=L0). 결정론 판정은 fixture 경로에만.
이 한 항목이 #1의 성격(검증완료 수준)을 가른다 — 가장 먼저 답할 것.
BR-C-2

ROS2 ↔ 우리 DDS interop

브리지 = rclcpp 노드가 ROS2를 받아 FastDDS 정규 타입으로 재발행(ROS2 type-hash 회피). 도메인: 정규 DDS는 VISS_DDS_DOMAIN_ID(기본 0), ROS2 rmw 도메인과 분리·매핑. QoS: 제어 평면 RELIABLE.

BR-C-3

실행 오케스트레이션 (MMF로 수렴)

SiLS 측 서비스(vECU·브리지·ClockMaster)는 MMF가 기동·관리(adsw_manager/lifecycle_mgr, speclist) — 경로 B가 vECU로 실증. 브리지를 MMF 서비스로 추가하면 오케스트레이션이 speclist 하나로 수렴. MORAI·Autoware는 외부 기동. 시나리오는 .xosc를 MORAI 러너/scenario_simulator_v2에 로드 → (b) importer가 같은 .xosc에서 요구를 뽑아 자극과 판정이 한 소스.

5 · 인수 기준 (Acceptance)

레벨확인 방법
연결브리지 기동 시 vECU가 state_received·target_received emit(실 데이터)
폐루프control_published가 실 상태에 반응 → gate.py FIDELITY PASS(closed_loop=true)
요구 판정.xosc → import_openscenario.py → gate.py --requirements → 요구별 pass/fail
결정론(L3)(BR-C-1 지원 시) 두 실행 control_published bit-동일
parity(L4)(후속) MORAI ground-truth 별도 캡처 + parity.py
최소 성공 = 연결 + 폐루프 + 요구 판정. 결정론(L3)은 BR-C-1에 종속.

6 · 열린 결정 (팀이 답할 것)

  1. [BR-C-1] MORAI 스텝 제어 지원 여부 — 결정론 L3의 생사. 최우선
  2. [BR-M-2] MORAI 종방향 명령 모드 — 가속도 직결 vs accel/brake 정규화(차량 파라미터 필요).
  3. [BR-A-2] Autoware 상태 피드백 경로 — MORAI 직접 vs 상태 브리지.
  4. 메시지 필드·단위 [확인] — morai_msgs/autoware_*_msgs 실제 정의로 §2·§3 표 확정.
  5. 좌표 프레임 정합 — MORAI map 프레임 ↔ 정규 EgoState map 프레임(원점·축).

7 · 범위 요약

버킷요구규모
BR-M MORAI 브리지상태 IN + 명령 OUT 번역중 (OUT 종방향 모드가 변수)
BR-A Autoware 브리지타깃 IN(거의 1:1) + 상태 피드백 경로소~중
BR-C 공통clock 확인 + interop + 오케스트레이션소 (BR-C-1은 리스크)
계약·vECU·판정·요구·시나리오—✅ 완료
두 브리지 + clock 확인 1 + interop/오케스트레이션 2 = #1 요구사항 닫힘. 번역 대상(양쪽 메시지·정규 계약)이 다 확정돼 범위가 명확하며, BR-C-1(MORAI 스텝 제어)만 먼저 답하면 나머지는 순수 번역·배관이다.
