# 증거 — C1 + MMF 가 한 도메인에서 같이 돈다 (TypeObject 고침 이후)

> 측정 2026-08-12 · **도메인 42 단일** · kashiwanoha · headless
> 선행: [`mmf-typeobject-2026-08-12.md`](mmf-typeobject-2026-08-12.md)
> — 고치기 전에는 이 구성이 파티션 3종에 `invalid type object` **1260줄**을 쏟았다
> (죽지는 않는다 — 그 문서 §4 의 정정 참고).
> 재현: `tools/sils/ss2/run_c1_with_mmf.sh`

목표 문장의 마지막 조각이 붙었다 — *"SS_v2 로 Autoware 연동하고 **MMF vehicle info
연동**하고 SiLS vECU 연동"*. MMF 는 여태 rig 에 없었고, 넣으면 Autoware 가 죽었다.

---

## 1. 배선

```
  SS_v2 (isEgo 없음) ─▶ ①ss2_ego_bridge ─▶ sils/ego/state ─┬─▶ ③ ─▶ /vehicle/status/*  ┐
                                                            └─▶ ④ ─▶ /localization/*   │
                                                                                        ▼
                   vECU 5기 ◀── autoware/control_target ◀── ② ◀── control_cmd ◀── Autoware
                                                                                        │
                                 MMF viss-server ◀── ADAPI ◀──────────────────────────┘
                                      └─▶ VSS 트리 (Vehicle.ADS.*)  60 경로
```

컨테이너 8개: 파티션 3 · 어댑터 4 · vECU 1 · MMF 1.

### ★ MMF 는 죽지 않은 게 아니라 일하고 있다

"파티션이 안 죽었다" 는 절반이다. MMF 가 실제로 ADAPI 를 읽어 VSS 로 내보내는지는
따로 봐야 한다:

```
DDSProvider: Pushing to channel -> Path: Vehicle.ADS.VehicleKinematics.Pose, Value: {...}
DDSProvider: Pushing to channel -> Path: Vehicle.ADS.Planning.Trajectory.PointCount, Value: 12
DDSProvider: Pushing to channel -> Path: Vehicle.ADS.IsEmergency, Value: false
```

**자차 위치가 SS_v2 → 우리 브리지 → Autoware → ADAPI → MMF → VSS 까지 흘렀다.**
경로 하나가 여섯 프로세스를 통과한다.

## 3. 차는 우리 명령으로 움직이지 않았다 — 그리고 그건 예상대로다

```
t=1  vx=5.0   3778.41  73801.01
t=2  vx=5.0   3791.09  73807.53
t=3  vx=5.0   3800.83  73812.54     ← 종점
t=4  vx=0.0   3800.83  73812.54
```

**`vx` 가 상수 5.0 이다.** C2(EgoEntity)에서는 곡선이었다 —
`0.000 → 1.524 → 2.586 → 1.955 → 0.000 → 0.651`.

`isEgo` 가 없으면 명령을 소비할 차량 모델이 아예 만들어지지 않는다
(`simple_sensor_simulator.cpp:201`). 차는 `LateralAction.LaneChangeAction` 각본이
움직인다. **C1 의 구조적 한계이고, MMF 와 무관하다** →
[`sils-configuration-map.md`](../sils-configuration-map.md) C1 주의.

## 4. 이 런에서 밟은 함정 셋 (전부 측정 쪽이었다)

**rig 는 멀쩡한데 측정이 거짓말을 했다.** 셋 다 증상이 "아무 데이터도 없음" 이라
rig 고장과 구분이 안 됐다.

| # | 증상 | 진짜 원인 |
|---|---|---|
| 1 | `ros2` 조회가 전부 빈 출력 → "아무도 발행 안 한다" | **ros2cli 데몬이 죽었다.** 프로세스는 남아 있고 조회만 실패한다: `xmlrpc.client.Fault: <Fault 1: "RuntimeError:!rclpy.ok()">`. stderr 라 `2>/dev/null` 에 먹혀 빈 출력이 된다 → **`--no-daemon` 을 쓴다** |
| 2 | 컨테이너 안 `awk $2` 가 빈 값 | `docker exec ... bash -lc "..."` 를 **큰따옴표**로 감싸 호스트 셸이 `$2` 를 먼저 먹었다 → **단일 인용 + `-e` 로 값 전달** |
| 3 | `engage: success=False` | 자차가 5 m/s 로 ~93 m 를 20초에 주파하는데 `--no-daemon` 조회가 건당 6~8초다. goal 과 engage 사이에 routing 조회를 끼웠더니 그동안 차가 종점에 닿아 **목표가 뒤로 가** 경로가 무효 → **goal 직후 engage, 조회는 나중** |

> ★ **셋 다 "빈 출력 = 아무 일도 안 일어남" 으로 읽혔다.** 이 rig 에서 빈 결과를 받으면
> **먼저 측정 도구를 의심할 것.** 브리지 카운터(`received=/published=`)는 데몬과 무관하게
> 돌므로, 그쪽이 살아 있으면 rig 는 살아 있는 것이다.

## 5. 재현

```bash
# 선행 — 파티션 3종, control 은 sps OFF
~/oss/oss_adsw/partition/run_partitions.sh --domain-id 42 --headless \
    --map-path "$HOME/autoware_map/kashiwanoha"
tools/sils/ss2/run_control_partition_sils.sh --domain-id 42 \
    --map-path "$HOME/autoware_map/kashiwanoha"

# 본체 (MMF·어댑터 4·vECU·시나리오·판정까지)
tools/sils/ss2/run_c1_with_mmf.sh --samples 20
tools/sils/ss2/run_c1_with_mmf.sh --no-mmf      # 대조군
```

⚠ MMF 는 **패치된 이미지**(`oss-mmf-core:local`)여야 로그가 깨끗하다. 패치 없는
`registry.obigo.com/oss/oss-mmf-core:latest` 는 파티션 로그에 1260줄을 쏟는다(죽지는 않는다).
로컬 빌드: `./build.sh && ./docker/build_local.sh --core-only`.
