SiLS · 시뮬레이터 연동

두 시뮬레이션 경로 아키텍처

루프 A — MORAI 와 루프 B — Web.Auto 시나리오 를 나란히 놓고, 어디까지가 우리 것인지를 색으로 표시한 그림. 핵심은 두 그림의 아래 절반이 완전히 같다는 것 — 바뀌는 것은 어댑터 컨테이너 하나뿐이고 service/sils/ 는 재빌드하지 않는다.

정본은 sils-simulator-loops.md — 충돌하면 .md 를 믿을 것.

범례 — scope 색

SiLS 소유 · 우리 저장소, 우리가 정본 우리가 만들 어댑터 · SiLS 밖, 부패 방지 계층 외부 오픈소스 · 온프렘, patch 가능 외부 상용 · 내부 접근 불가, 벤더 문의 클라우드 SaaS · 자산만 반출
어댑터가 왜 SiLS 밖인가. 어댑터는 시뮬레이터마다 다르고 벤더 사정으로 흔들린다. 이것을 안에 넣으면 시뮬레이터를 바꿀 때마다 service/sils/ 가 흔들린다 — 그래서 어댑터를 부패 방지 계층으로 밖에 두고, SiLS 는 정규 계약 (EgoState/VehicleControl/ControlTarget)만 소유한다.

루프 A 의 위험은 배선이 아니라 단위다. deg 를 rad 로 안 바꾸면 값이 57.3배로 들어오는데, 코드는 아무 데서도 실패하지 않고 판정만 조용히 틀린다. MORAI 는 안을 못 여니 이런 것을 소스로 확인할 수 없다 — B 를 먼저 하는 이유다.

두 경로 비교

루프 B — Web.Auto 시나리오루프 A — MORAI
시뮬레이터 scenario_simulator_v2 오픈소스 MORAI 상용
자극원 Web.Auto Editor 저작 .xosc MORAI 시나리오 러너
판정 기준 같은 .xosc 에서 자동 추출 별도 저작 (어긋날 여지)
막혔을 때 소스를 읽어 푼다 — B1-1 이 실제로 그랬다 벤더 답변을 기다린다 — A1-1~A1-4
시간/결정론 조사 완료 — 그대로는 L3 불가, 개조하면 가능 (W3) 미확인 — BR-C-1 답에 종속
예상 fidelity B-det L3 / B-full L0~L1 L0 ~ L3 (A1-1 에 종속)
어댑터 난이도 낮음 — rad·m/s² 이미 1:1 높음 — 단위 변환 3종 + 명령 모드
우리 코드 변경 양쪽 모두 0 — IDL · vECU · barrier · 게이트 전부 그대로
이 그림의 결론 한 줄. 두 경로의 차이는 전부 스위치 지점 위쪽에 있다. 아래쪽(SiLS 소유)은 같은 바이너리·같은 채널맵·같은 게이트라서, 둘을 병행해도 유지 비용이 두 배가 되지 않는다. 대신 판정 결과를 섞으면 안 되므로 golden 을 플랜트별로 격리한다.

가장 자주 나오는 오해. “Web.Auto 를 고쳐서 붙인다” 가 아니다. Web.Auto 는 클라우드 SaaS 라 접근 자체가 불가능하고, 필요하지도 않다. 우리가 patch 를 고민하는 대상은 온프렘에서 우리가 띄우는 오픈소스 scenario_simulator_v2 이며, 그중에서도 traffic_simulator 의 updateFrame() 구동부와 openscenario_interpreter 의 create_wall_timer 두 곳이다.
