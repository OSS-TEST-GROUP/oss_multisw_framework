SiLS 에이전트 자동화

LLM 에이전트로 검증 자동화 · 판정은 conformance kit, 에이전트는 그 앞뒤 · 설계 제안 · 2026-07

SiLS는 판정이 이미 결정론 코드(gate.py/evaluate.py)에 있고 산출물이 전부 기계판독이다. 그래서 앞단(입력 생성)과 뒷단(실패 해석·리포트)은 에이전트로 자동화할 수 있다. 판정 자체는 불가 — 에이전트 출력은 증거가 아니라 가설이다.
이 문서는 설계(제안)다. §3 파이프라인은 이미 있는 것, §5 에이전트 계층은 아직 없는 것. 정확한 본문은 sils-agent-automation.md.

1. 왜 SiLS가 에이전트 자동화에 유리한가

에이전트 자동화가 실패하는 전형적 원인은 "결과가 좋은지 나쁜지를 LLM이 판단해야 하는" 구조다. 판정이 확률적이면 CI로 쓸 수 없고 회귀 방어선이 되지 못한다. SiLS는 그 반대로 설계돼 있다.

이미 갖춰진 것근거자동화에 주는 의미
판정 = 결정론 코드gate.py — SCHEMA→FIDELITY→PARITY, fail-closed, 단일 exit code에이전트가 채점자가 될 필요가 없다
판정 경계 = 트레이스"실행이 남긴 JSONL이 공개 conformance 경계"(extension-model §2)소비할 입력이 명세된 구조체(trace-schema/v1.json)
구조화된 실패 증거verdict.json의 violations[] + analyzer별 섹션실패 해석을 트레이스 전문 없이 시작
재현성lockstep tick · recv_seq staging · tick_seq 고정 결함 스케줄 · FMU 순수함수"다시 돌려 확인"이 의미 있는 행위가 된다
단일 진입점 + 단계 skipsils-ci.sh (--traces-dir/--dry-run/--resolved)바이너리 없이도 전 구간을 다룰 수 있다
병렬 격리domain_lease.py — 유한 pool·TTL·owner 임대fan-out이 DDS domain 충돌 없이 가능

한 줄 요약: 채점기가 이미 있으므로, 에이전트는 채점을 하지 않고 채점의 앞뒤를 맡는다.

2. 근본 경계 — 에이전트는 판정에 들어가지 않는다

2.1 왜 이 경계인가

evaluate.py의 conformant는 verdict == "PASSED" and not violations — 단일 불변식이다. 여기에 "그런데 이 violation은 사소해 보입니다"가 끼면:

  • 재현성 상실 — 같은 트레이스가 실행마다 다른 결론을 낼 수 있다. "같은 입력 → 동일 판정" 논거(tool-confidence §2)가 깨진다.
  • 제3자 재생산 불가 — OEM·안전팀이 같은 트레이스로 같은 결론을 얻는다는 보장이 사라진다.
  • 녹색 편향 — 에이전트는 태스크를 "완료"하려는 압력을 받는다. 판정 권한을 주면 실패를 통과로 만드는 방향으로 흐른다(§6).

2.2 파생 규칙 — 에이전트 쓰기 금지 경로

판정 기준 자체를 수정하는 것은 판정에 참여하는 것과 같다. 단 대상을 두 종류로 나눠야 한다 — 전부 금지하면 정당한 개발까지 막힌다.

2.3 강제는 2층 — 규칙을 어디에 두는가가 내용보다 중요하다

이 규칙은 개발자별 설정이 아니다. 각자 설정하면 보증이 사라진다 — 한 명이 설정하지 않은 채로 tolerance 완화를 커밋하면 그걸로 끝이다. .clang-tidy를 리포에 커밋하는 것과 같은 범주다.
파일범위git무엇을 담나
.claude/settings.json프로젝트 공유커밋§2.2 규칙. clone한 모든 개발자에게 적용 — 복사 배포 불필요

~/.claude/settings.json개인 전역—개인 취향. §2.2를 여기 두면 안 된다

로드 순서는 user → project → local(뒤가 앞을 덮음)이지만, 권한 규칙은 목록이 누적되고 deny가 allow를 이기므로 개인 설정으로 공유 deny를 되돌릴 수는 없다.

settings.json 하나로는 보증이 되지 않는다. deny는 Edit/Write를 막지만 Bash 우회가 가능하다(sed -i, > file, python -c). .claude/settings.json 자체도 리포 파일이라 편집할 수 있다.

3. 현재 파이프라인과 에이전트가 붙는 지점

evaluate.py가 run당 내보내는 필드가 그대로 에이전트 입력 스키마가 된다:

필드트리아지에서의 역할
verdict / terminal_sourcePASSED·FAILED·ABORTED·INCOMPLETE + 누가 그 판정을 냈는지(coordinator/verifier)
conformant최종 게이트 (PASSED && violations 없음)
fidelity_evidenced어느 충실도까지 증거가 있었나 (L0~L4)

clock·staging·behavior·plant·vehicle·scenario·faultanalyzer별 요약 — 어느 축이 깨졌는지
attestationL4 게이트 (arch/gateway/protocol)
instance_ids / domainsfleet 완전성 · 격리 확인
evidence.{endpoints_matched,samples_received,verify_pass}L0 증거

4. 전제 — 자동화의 첫 조각은 에이전트가 아니다

SiLS는 현재 CI에 연결돼 있지 않다. Jenkinsfile·Jenkinsfile.integration·Jenkinsfile.unittest·.github/workflows/* 전체에 sils 참조가 없다. 즉 artifact를 정기적으로 생산하는 주체가 없다. 에이전트는 소비자이므로 소비할 것이 먼저 있어야 한다 — 순서를 뒤집으면(에이전트가 매번 직접 빌드·실행) 느리고 불안정하고 재현되지 않는다.
전제왜 필요한가형태
P0-a. CI 스테이지정기·재현 가능한 artifact 생산Jenkins에 sils-ci.sh 스테이지 1개 (--traces-dir 경로부터 시작 가능)
P0-b. artifact 보존 규약에이전트가 "지난번"과 비교할 수 있어야 함runs/<run_id>/{resolved-run.yaml,traces/,verdict.json,junit.xml,compare/,parity/} N일 보존

4.1 플랫폼 제약 (실측)

환경vECU 본체(C++)도구 계층(py/sh)에이전트 루프 가능 경로

로컬 에이전트 작업은 사전 캡처 트레이스 기반으로 설계해야 한다. sils-ci.sh가 이 경로를 이미 1급으로 지원한다(주석: "샌드박스 테스트 가능 경로"). 트리아지·리포트·드리프트 감시는 전부 이 경로로 개발·검증 가능하다.

4.2 실행 주체 — Phase 1(사내) → Phase 2(국내 공개·연구)

"개발자가 자기 ECU를 올려 검증받는다"가 이 플랫폼의 방향이다. 다만 누가 올리는가에 따라 요구가 완전히 달라지고, 그건 2단계로 계획돼 있다.

실행 환경 제공자는 부수적 인프라가 아니라 판정 권위의 일부다. 누가 어디서 돌렸는지가 신뢰 수준을 정한다 — parity.py의 attestation 게이트(arch/gateway/protocol)가 정확히 그것을 검사한다.

Phase 1에서는 실행/판정 분리가 필요 없다. 사내는 신뢰 문제가 없으므로 CI가 그냥 빌드·실행·판정을 다 한다. self-hosted Jenkins가 오히려 정답이다. 따라서 §7의 0단계 → P0 → P1 순서가 그대로 유효하다.

Phase 2에서 실행/판정을 분리할 수 있다는 것이 이 아키텍처의 이점이다. gate.py는 trace만 소비하고 trace.jsonl은 데이터이지 코드가 아니다. 그래서 남의 코드를 실행하지 않고도 판정할 수 있다 — --traces-dir가 정확히 그 경로다.

Tier A만으로도 실수의 대부분(스키마 위반·계약 위반·lockstep 깨짐·fleet 불완전)이 잡힌다. 그리고 자기신고 trace의 신뢰 수준을 표현할 어휘가 이미 있다: parity.py의 PARITY_UNATTESTED(=L3 상한). 새 개념을 만들 필요가 없다.

Phase 2의 최우선 가치는 재현성이다. 연구자에게 핵심 질문은 "내 결과를 남이 재현할 수 있는가"이고, SiLS는 이미 그것을 갖고 있다 — 같은 입력 → bit-동일 trace → 동일 판정(tool-confidence §2). capture_golden/compare_golden이 그대로 연구 재현 도구가 된다. 나중에 덧붙일 기능이 아니라 이미 결정된 강점이다.

공개 대상이 국내이므로 한국어 문서는 그대로 자산이다(문서 영어화는 Phase 2 범위 밖).

7.2 P0에서 지금 지킬 것 (Phase 2 대비)

Phase 1의 CI를 Jenkins에 붙이는 것은 맞지만, §4.2의 Phase 2(공개·GitHub Actions)를 아는 지금 잘못 굳히면 나중에 비싸지는 결정들이 있다.

지킬 것안 지키면
sils-ci.sh를 감싸지 말고 그대로 호출Phase 2에서 GitHub Actions로 갈아탈 때 Jenkinsfile 안의 로직을 다시 쓴다. 단일 진입점으로 설계된 성질을 버리지 말 것
builder 이미지를 공개 가능한 형태로사내 registry(IMAGE_REGISTRY + 자격증명) 의존을 굳히면 Phase 2에서 전면 재작업. BUILD_SILS 기본값도 같이 정리
artifact 레이아웃을 CI 도구 중립으로Jenkins 관례(output/integration-results/**)에 묶이면 GitHub Actions에서 재사용 불가
토폴로지·예제를 늘릴 때 문서와 함께Phase 2의 진입 장벽이 여기서 결정된다. 대학원생이 30분 안에 첫 vECU를 돌릴 수 있어야 한다

그리고 §2.2의 두 항목이 Phase 2에서 선택이 아니라 필수가 된다: config/sils/fmu/(외부인이 임의 FMU를 올림 = in-process 네이티브 코드 실행)와 CODEOWNERS(외부 컨트리뷰터가 판정 기준을 만짐).

8. 상태

  • 설계 제안. 구현된 에이전트 계층은 없다(§7 그림 4).
  • 감싸는 대상(§3)은 존재하며 도구 계층은 실행·테스트 완료 — tools/sils/README.md 검증 상태 참고.
  • Phase 1(사내)이 현재 단계. 실행 주체는 사내 Jenkins로 정해졌다(§4.2) — Tier A/B 분리는 Phase 2 사항이므로 지금 구현하지 않는다.
  • 선행 결정 필요: artifact 보존 기간·위치 · golden 디렉터리 경로(§7.1).
