MMF SiLS · 이해 다이어그램 · 1장 Topology Compiler

정적 변환·검증은 언제, 어떻게, 어디서 일어나는가

SiLS 가상 ECU 전체를 훑는 이해 문서의 1장 다이어그램. 토폴로지 컴파일은 실행(launch) 전에 한 번 돈다 — YAML 4종을 읽어 잘못된 조합을 실행 전에 잡고(검증), 맞으면 실행 가능한 계획으로 펼친다(변환). DDS·도커·빌드·arm64 없이 도는 순수 정적 단계. (장이 늘면 다이어그램도 여기에 추가된다.)

판정

trace → evaluate

런타임 conformance 검증(6장) · 회귀/패리티(8·10장).

검증은 이 한 곳(compile)만이 아니다. 3계층으로 흩어진 cross-cutting 주제다 — ① 정적 계획 검증(카탈로그 lint + 토폴로지 compile, 이 다이어그램·1장) · ② 런타임 conformance(trace→verdict, evaluate.py, 6장) · ③ 회귀·패리티(compare_golden·parity, 8·10장). 이 다이어그램은 ①만 그린다.

앞에서 한 번

compile은 CI/PR/pre-commit에서 launch보다 앞서 실행. 문제를 실행 전으로 당겨 잡는 shift-left.

실행은 신뢰

Coordinator는 --from-resolved로 이미 검증된 계획을 소비만. 컴파일러를 다시 호출하지 않는다.

순수 정적

DDS·도커·빌드 불필요. 16개 테스트가 실런타임 없이 커버. 어느 머신·샌드박스에서든 동일.

vECU 컨테이너  (arm64 또는 x86)C++ 만

sils_vecu_viss_probeSILS_* env 읽고 DDS publish. Python 없음. 검증 안 함.

검증은 arch 중립

x86 맥에서든 CI 러너에서든 같은 판정. arm64 불필요.

arm64는 런타임용

probe C++ 바이너리를 arm64로 빌드·실행하는 것. L4 attestation(arch=aarch64)이 증명하려는 부분.

vECU엔 Python 불필요

probe는 C++이고 SILS_* env만 읽는다.

Fail-closed가 핵심: 에러가 하나라도 있으면 compile_topology는 (None, None, errors)를 반환하고 아티팩트를 아예 쓰지 않는다 — 잘못된 실행 계획이 하류로 새지 않는다. resolved-run.yaml 존재 = 그 순간의 입력에 대해 검증 통과이며, input_hashes로 현재 소스와의 drift를 검증할 수 있다(자동 대조는 미구현).
