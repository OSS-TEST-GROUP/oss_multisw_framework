04  계약 = SUT ↔ vECU 합의 (+ QoS 매칭)

IDL 은 타입만 정의한다. "어느 topic·domain 에서, 어떤 QoS 로, 누가 발행/구독하나"는 계약이 선언한다. DDS 는 양쪽이 맞아야 통신이 성립하므로, 이 합의를 파일로 고정하고 정적 검증한다(검증은 1장).

◀ subscribe

QoS 는 "하나"가 아니라 정책(policy)의 묶음

ReliabilityBEST_EFFORT · RELIABLE
DurabilityVOLATILE · TRANSIENT_LOCAL · TRANSIENT · PERSISTENT
HistoryKEEP_LAST(depth) · KEEP_ALL
Deadline · Liveliness · Ownership …그 외 다수

TRANSIENT_LOCAL 은 QoS 자체가 아니라 Durability 정책의 한 값. 카탈로그의 "프로파일"(예: viss-sils-verifiable)은 이 정책 값들을 묶은 세트다.

QoS 는 "협상(nego)"이 아니다 — RxO 호환성 판정이다. Writer 는 자기 QoS 를 독립적으로 제공(Offered), Reader 는 독립적으로 요청(Requested) — 통신 전에 각자 미리 정한다. discovery 때 DDS 는 호환성만 판정: 제공이 요청을 만족하면 매칭, 아니면 침묵(데이터 0) + incompatible_qos 이벤트. 중간값 타협도, 값 변경도 없다 — 그래서 카탈로그로 미리 호환되게 고정한다.
durability: Writer TRANSIENT_LOCAL ⊒ Reader VOLATILE → late-join reader 도 히스토리 수신 ✓ (matched-but-no-data 해결)
reliability: Writer RELIABLE ⊒ Reader BEST_EFFORT/RELIABLE · Writer BEST_EFFORT 는 RELIABLE reader 못 만족 ✗

09  도메인 임대 — 병렬 run 격리 (§12)

DDS 는 domain id 로 통신을 격리한다. 병렬 run 이 서로 샘플이 안 섞이려면 다른 domain 을 써야 하는데 domain 은 유한 → 유한 pool 에서 임대.

atomic 획득

O_CREAT|O_EXCL per-domain 파일 — 두 러너 race 를 OS 가 차단. pool 소진 시 exit 3.

TTL + owner_pid

Coordinator 가 release 없이 죽어도 만료되면 reap 이 회수 → domain 누수 방지(§14.4).

pool 분리

--lease-dir 로 러너별 pool 분리 → CI 간섭 차단(§12.2). 도구는 메커니즘, pool 배정은 정책.

inject vs allocate

--domain 직접 주입(SUT domain 에 붙일 때, §3.4) / --domain-pool 임대(병렬 격리).

teardown 은 idempotent, reap 은 안전망: state 파일(CONTAINER_NAME· PROBE_PID·DOMAIN_LEASED)을 docker run 전에 먼저 적어, run 도중 죽어도 컨테이너·PID·lease 를 회수할 수 있다(§14.4 crash 안전). 두 백엔드는 같은 host-side verify 를 쓰며, docker 는 --ipc=host 가 없으면 SHM 경로가 끊겨 matched-but-no-data(2026-07 실측).

10  컨테이너 실행 & MMF 통합 (누가 띄우나)

이미지의 엔트리포인트는 probe 를 PID 1 로 exec — 컨테이너 수명이 곧 probe 프로세스다(docker stop→SIGTERM 직접→graceful). vECU 를 실제로 띄우는 주체는 두 경로가 있다.

docker run -d -e SILS_*=…  -e VISS_DDS_DOMAIN_ID=90 <image>
  └─ entrypoint.sh ──exec──▶ sils_vecu_viss_probe (PID 1)
                               └─ getenv(SILS_*) 로 포트 선택 ──▶ DDS publish   # 컨테이너 수명 = probe

entrypoint·이미지는 범용 — "실 vECU 정보"는 세 군데로 나뉜다

① 로직(구현)probe 바이너리 (컴파일 baked) — 모든 포트 구현. env 가 하나 선택
② 선택·파라미터·경로SILS_* env (런타임 주입) — behavior·Kp·faults·FMU 경로
③ 모델 데이터컨테이너 파일시스템 — 실제 .fmu·replay (env 는 PATH 만)

entrypoint 에는 vECU 정보가 전혀 없다 — 모든 인스턴스가 동일 이미지·entrypoint. 실행 중 정체 확인: docker inspect … | grep ^SILS_.

11  멀티 인스턴스 — "N 컨테이너 = N 인스턴스"

vecus[]×replicas 를 compile 이 N 컨테이너로 전개(resolved-run·saved-service-list 둘 다). 단 한 컨테이너/프로세스 = 정확히 1 인스턴스 — entrypoint 가 probe 하나만 exec 하므로.

topology.vecus[]  ──expand──▶  c1 (instance_id=ws-1) → probe(PID1)   ┐
                               c2 (instance_id=ws-2) → probe(PID1)   ├ fleet: 도메인 1개 공유,
                               c3 (instance_id=ws-3) → probe(PID1)   │ 동시 기동
                               c4 (instance_id=ws-4) → probe(PID1)   ┘

여러 인스턴스 = 분리된 N 컨테이너/프로세스(각자 instance_id), fleet 이 도메인 1개 공유해 동시 기동. 한 프로세스에 여러 vECU 를 넣는 in-process 다중화는 fmi4c thread-safety 시험 전 미허용(plant.hpp) — 지금은 "프로세스=인스턴스" 모델.
