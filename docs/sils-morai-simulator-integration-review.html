SiLS–MORAI Simulator 연동 아키텍처 검토

대상: oss_multisw_framework SiLS와 MORAI 차량 시뮬레이터 연동
범위: 차량 제어/상태, 센서, 시간 동기화, 시나리오 자동화, 네트워크, 시험·운영

1. 검토 결론

MORAI를 외부 Plant/Sensor Simulator로 두고 검증 중인 한양대 UDP–ROS2 Bridge를 재사용한다. SiLS는 Bridge를 외부 runtime component로 관리하며, K-Autoware 표준 타입이 누락된 endpoint에만 선택적 Contract Adapter를 둔다. 최초 구현은 WallClock + live 폐루프로 제한한다.

단순 ROS/UDP 브리지로 정의하면 차량 동역학의 중복 계산, 시간축 불일치, 좌표 변환 오류와 대용량 센서 병목이 뒤늦게 드러날 수 있다. 가장 먼저 확정할 것은 통신 프로토콜이 아니라 차량 상태의 단일 권위자와 시간 진행 방식이다.

2. 연동 전에 결정할 사항

2.1 차량 동역학 소유권

구성동역학 소유자MORAI 역할판단
A. MORAI PlantMORAI차량 물리, 환경, 센서초기 권장
B. External PlantMMF FMU/IPlant시각화, 환경, 센서 렌더링동역학 FMU 검증 목적

A안에서는 ADSW가 조향·가속·제동·기어를 보내고 MORAI가 pose·velocity·acceleration·gear를 반환한다. B안에서는 MMF가 계산한 pose를 Ego Ghost Mode 등으로 MORAI에 주입한다. 어느 경우든 MORAI와 MMF가 동시에 차량 위치와 속도를 계산해서는 안 된다.

simulator:
  kind: morai
  vehicle_state_authority: morai   # morai | external-plant
  time_mode: wall                  # wall | synchronous

2.2 연동 성공 기준

  • Coordinator가 MORAI readiness와 scenario 상태를 판정한다.
  • 고정 scenario를 load/reset하고 Ego 초기 상태를 재현한다.
  • 제어 publisher는 run당 하나만 존재한다.
  • command timeout 시 합의된 safe command로 전환한다.
  • 상태에 source/receive timestamp와 sequence가 존재한다.
  • 좌표, yaw, 속도, 조향 golden sample을 통과한다.
  • MORAI 종료와 network 단절을 run failure로 처리하고 정리한다.

3. Control Plane과 Data Plane 분리

3.1 Control Plane

MSC, gRPC 또는 ROS service로 simulator 실행 확인, map/scenario load, Ego/센서 설정, reset/start/pause/stop과 종료를 관리한다. 제품 문서의 기능이 설치 버전과 라이선스에서 실제 제공되는지는 capability spike로 확인한다.

3.2 Data Plane

방향데이터단계
MMF → MORAIsteering, accelerator/throttle, brake, gearP0
MORAI → MMFpose, velocity, acceleration, yaw, gearP0
MORAI → MMFGPS, IMU, object, traffic lightP1
MORAI → MMFCamera, LiDAR, RadarP2

3.3 프로토콜 판단

  • ROS/ROS bridge: 메시지 기반 상태·센서. ROS1/ROS2와 custom morai_msgs 호환성 확인.
  • UDP: 제어·상태·고빈도 센서. schema, sequence, loss, fragmentation, endian, port 관리 필요.
  • MSC/gRPC/API: 시나리오와 lifecycle용. 고빈도 센서 경로로 사용하지 않는다.
  • CAN: ECU fidelity가 필요할 때 장비, DBC와 라이선스 확인 후 도입한다.

3.4 2024-12-09 협의 내용의 현재 해석

당시 MORAI 회신은 일반/Semantic/Instance Camera는 CompressedImage, Depth는 Image, RADAR는 morai_msgs/RadarDetections, LiDAR는 PointCloud2, GPS는 morai_msgs/GPSMessage, IMU는 Imu이며 ROS2/DDS는 공식 미지원이라는 내용이었다.

이는 당시 납품 버전 기준선으로 보존하되 현재 기능으로 단정하면 안 된다. 2026-07 확인 시 MORAI 공식 GitHub에는 ROS2 메시지와 example 저장소가 공개되어 있고 CtrlCmd, EgoVehicleStatus, GPSMessage, RadarDetections 등이 존재한다.

공개 ROS2 저장소 존재가 납품 제품의 공식 지원이나 K-Autoware 직접 호환을 의미하지 않는다. 대상 build의 ROS2 지원·유지보수·QoS를 공급사에 다시 확인한다.

ROS2/DDS 직접 통신에는 동일 schema/version, type name/hash와 CDR, topic/namespace, QoS, ROS_DOMAIN_ID, discovery/RMW 호환성, timestamp/frame이 모두 맞아야 한다. 한양대 Bridge가 변환을 이미 검증했다면 별도 Adapter를 중복 구현하지 않고 Supervisor/Contract Validator만 둔다.

3.5 Sensor 데이터 포맷 Gap

SensorK-Autoware 요구MORAI 제공판정 및 Adapter 요구
Camerasensor_msgs/Image일반/Semantic/Instance: CompressedImage
Depth: Image		부분 불일치. 압축 해제 후 Image republish, encoding/step/endian/timestamp 보존
RADARradar_msgs/RadarTracksmorai_msgs/RadarDetections의미·구조 불일치. tracker 또는 MORAI tracked output 필요
LiDARsensor_msgs/PointCloud2sensor_msgs/PointCloud2타입 일치. fields/frame/time/intensity/ring/endian 검증
GNSSsensor_msgs/NavSatFixmorai_msgs/GPSMessage타입 불일치. status/covariance/altitude datum 변환
IMUsensor_msgs/Imusensor_msgs/Imu타입 일치. frame/unit/gravity/covariance 검증

Camera

Depth의 Image는 일반 RGB 요구를 대체하지 않는다. RGB/Semantic/Instance에는 decode가 필요하며 rgb8/bgr8/mono8/16UC1/32FC1 등 encoding, optical frame, source timestamp, semantic palette를 계약한다. perception이 calibration을 쓰면 요구 목록에 없는 CameraInfo도 endpoint로 추가한다.

RADAR

RadarDetections[]를 이름만 바꿔 RadarTracks[]로 만들면 안 된다. RadarTrack은 stable UUID, position, velocity, acceleration, size, classification과 covariance를 요구한다. MORAI가 이를 제공하지 않으면 tracked output 요청, 별도 tracker, 또는 K-Autoware 입력 변경 중 하나를 선택한다. unknown covariance를 0으로 채우면 오차 없음으로 오해될 수 있다.

LiDAR

header.frame_id, TF, point/row step, x/y/z/intensity/ring/return/time fields, datatype, byte order, 좌표축, NaN과 is_dense를 golden capture로 비교한다.

GNSS

MORAI GPSMessage의 latitude/longitude/altitude를 변환하고 east/north offset은 별도 local pose 계산에 사용한다. MORAI 공개 설명은 sea-level altitude이고 NavSatFix는 WGS84 ellipsoid altitude를 기대하므로 geoid separation 정책이 없으면 수직 오차가 발생할 수 있다. NavSatStatus, covariance type과 source timestamp도 계약한다.

IMU

angular velocity rad/s, acceleration m/s², 중력 포함 여부, quaternion 축/정규화, covariance unknown 표현과 imu_link TF를 검증한다.

3.6 Controller와 Vehicle Status Gap

전달 내용에는 controller 스크린샷 파일명만 있고 이미지 자체는 현재 저장소에서 확인되지 않았다. 아래 mapping은 전달된 메시지 목록과 공개 정의 기준이며, 이미지에만 있는 topic·port·제어 mode는 파일 확보 후 보완한다.

K-Autoware → MORAI

Critical unit gap: 공개 MORAI 메시지에서 CtrlCmd.front_steer 입력은 rad이지만 EgoVehicleStatus.front_steer 출력은 deg다. Ego angular velocity는 deg/s, Autoware heading rate는 rad/s다. 누락 시 약 57.3배 오차가 발생한다.

제공된 VehicleEmergencyStamped 링크는 잘못된 ControlModeCommand.srv를 가리킨다. 실제 TIER IV 메시지는 timestamp와 boolean emergency로 구성되므로 링크를 교정한다.

3.7 권장 Bridge 배치

[ROS1 build] MORAI ROS1 → ROS1 ingress → Contract Adapter → ROS2 K-Autoware
[ROS2 build] MORAI ROS2 ──────────────→ Contract Adapter → ROS2 K-Autoware
[UDP build]  MORAI UDP  → 검증된 UDP–ROS2 Bridge → [선택 Adapter] → K-Autoware

schema·단위·좌표 변환, freshness, watchdog과 diagnostics의 최종 소유자를 계약으로 명시한다. 외부 Bridge가 검증한 기능은 중복 구현하지 않되 SiLS가 종단 결과를 독립 검증한다.

3.8 한양대 UDP–ROS2 Bridge 적용 결론과 SiLS 역할

제공된 MORAI Network Settings 화면에서 Ego-0는 Connected, Cmd Control은 UDP, Target Frame은 50Hz이며 개발 환경 Host/Destination은 127.0.0.1이다. 데이터별 port 구조를 사용하고 화면에 보이는 Collision Data 예시는 host 9091, destination 9092다.

MORAI Simulator ── UDP ──▶ 한양대 UDP–ROS2 Bridge ── ROS2/DDS ──▶ K-Autoware
                 ◀─────── controller command ◀──────────────────

localhost와 port는 캡처 환경의 예시이며 운영 계약값이 아니다. 분리 host/container 배치에서는 topology가 실제 IP, port block, firewall과 host networking을 생성한다.

4. 현재 MMF와의 접점

4.1 /VIN/Vehicle은 센서 입력 경로가 아님

config/sils/contracts/mmf-endpoints.yaml의 /VIN/Vehicle은 VISS 클라이언트가 서버에 보내는 VissRequestTopic이다. MORAI vehicle status나 sensor sample을 여기에 publish해서는 안 된다.

MORAI UDP
      ▼
한양대 UDP–ROS2 Bridge
      ▼ morai_msgs 또는 canonical K-Autoware ROS2
[선택적 MoraiContractAdapter]
      ▼ canonical Autoware DDS/ROS message
Vehicle Info Manager DDSProvider
      ▼
VSS/VISS data

4.2 기존 DDSProvider 재사용

현재 DDSProvider.cpp는 rt/api/vehicle/kinematics, rt/api/vehicle/status, perception objects, traffic signals와 orientation 등 Autoware 타입을 구독한다. Bridge가 canonical 타입을 제공하면 기존 경로를 재사용하고, morai_msgs까지만 제공하는 endpoint만 선택적 Adapter에서 변환한다.

Camera/LiDAR/IMU 원본은 VISS 변환이 필요한 semantic data와 ADSW가 직접 소비할 raw sensor data로 분리한다.

5. 시간 동기화와 결정성

5.1 초기 단계

run:
  input_mode: live
clock:
  mode: wall
simulator:
  determinism: best-effort

실제 sensor rate, command-to-state latency, source/receive timestamp 차이, sequence gap, real-time factor와 stale 횟수를 측정한다.

5.2 lockstep 도입 조건

  1. simulator를 확실히 pause할 수 있다.
  2. 정확히 한 step 또는 지정한 dt만 진행한다.
  3. 해당 step의 차량 상태와 필수 센서 완료를 알 수 있다.
  4. 외부 계산이 끝날 때까지 다음 step이 진행되지 않는다.
  5. 모든 출력이 같은 simulation time을 사용한다.
  6. timeout 이후 reset/abort가 가능하다.

pause/resume API만으로 lockstep을 보장할 수 없다. 센서 완료 barrier가 없다면 vehicle state와 Camera/LiDAR가 다른 step에 속할 수 있다.

5.3 replay 제한

입력을 replay해도 live ADSW의 출력까지 통제되는 것은 아니다. 입력 어댑터 회귀, open-loop 검증, 장애 재현 또는 SUT 출력까지 함께 기록한 완전 재생으로 범위를 한정한다.

6. 좌표계·단위·계약

지도 CRS/EPSG, UTM zone 또는 ENU origin, map/odom/base_link/sensor frame, 축 방향, yaw convention, quaternion ordering과 변환 책임자를 확정한다. raw Velodyne LiDAR와 ROS driver 변환 후 좌표를 동일하다고 가정하면 안 된다.

7. 네트워크·성능·병렬 실행

  • simulator host/destination IP, NIC, routing, firewall, VM bridge/NAT를 topology로 관리한다.
  • run별 UDP port block을 할당하고 종료 시 회수한다.
  • ROS master/bridge 또는 ROS2 discovery 범위를 run 격리 정책과 맞춘다.
  • Camera/LiDAR/Radar는 VISS JSON이나 범용 string payload로 운반하지 않는다.
  • 평균 rate 외에 p95/p99 latency, drop, out-of-order, CPU/GPU/NIC 사용량을 측정한다.

headless 지원, license당 동시 instance, CI/VM 활성화, GPU 사양, 자동화 API edition과 map asset 배포 권한은 공급사 확인이 필요하다.

8. 안전·장애 처리·진단

8.1 제어 안전

  • 명령 publisher를 run당 하나로 제한한다.
  • 수동 입력, MORAI 내부 제어, ADSW의 우선순위를 명시한다.
  • timeout 시 throttle 해제와 brake 적용 등 합의된 safe command를 보낸다.
  • reset 중 command를 차단하고 stale vehicle state를 정상 전달하지 않는다.

8.2 Adapter 진단

시나리오   loaded/running/paused/failed
제어       owner, last command, timeout
freshness  endpoint별 source/receive timestamp
전송       gap, drop, out-of-order, decode failure
변환       unit/frame/schema error
시간       skew, regression, duplicate timestamp
성능       actual rate, latency, queue backlog

Diagnostics Manager에는 raw 센서를 보내지 않고 위 health 요약과 원인을 표준 Component Health 계약으로 보고한다.

8.3 Coordinator 장애

run lease/heartbeat, coordinator-loss watchdog, idempotent stop, 재시작 후 orphan 탐색, process와 port 회수가 필요하다.

9. 시나리오 재현성과 형상관리

run manifest에 MORAI version/build/edition, map·scenario·vehicle·sensor config hash, initial pose, traffic/weather/friction, seed, adapter/contract version, MMF image digest, clock mode/dt/real-time factor, endpoint IP/port/topic을 기록한다. 비결정적 live run은 허용 오차 기반으로 판정한다.

10. 단계별 개발 권고

Phase 0A — Capability Spike

  • 제품/버전/edition과 ROS1/ROS2/UDP/MSC/gRPC 실사용 여부
  • scenario load/reset/status 자동화
  • timestamp와 sequence, synchronous step 및 sensor barrier
  • headless/병렬 실행/license 조건과 Ego Ghost Mode 범위
  • 한양대 Bridge packet/port map과 ROS2 topic/type/QoS/rate inventory
  • canonical 변환 범위, reconnect/stale/watchdog/safe-stop 검증

Phase 1 — Ego Control/Status Vertical Slice

차량·맵·시나리오 각 하나, MORAI 동역학, 한양대 Bridge 한 개를 external 또는 managed component로 등록하고 Bridge readiness/필수 ROS2 match를 확인한다. steering/accelerator/brake/gear와 pose/velocity/gear, WallClock/live로 제한하며 직진·정지·좌우 조향 golden scenario, timeout과 disconnect 시험까지 완료 조건으로 둔다.

Phase 2 — 자동화와 Semantic Data

scenario load/reset, GPS/IMU, object/traffic light, recorder, artifact manifest, adapter diagnostics, port allocator와 orphan cleanup을 추가한다.

Phase 3 — Raw Sensor와 결정성

Camera/LiDAR/Radar, 대역폭 최적화, 다중 Ego, fault injection을 추가한다. synchronous/lockstep은 step API와 sensor barrier가 검증된 경우에만 적용한다.

12.1 SiLS v3 아키텍처 반영 필요사항

기존 v3의 Topology Compiler, Run Coordinator, Contract Catalog, WallClock/live, readiness와 artifact 원칙은 그대로 유효하다. 핵심 재설계는 필요 없지만 다음을 보강한다.
