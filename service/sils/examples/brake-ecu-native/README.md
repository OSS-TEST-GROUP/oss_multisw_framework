# brake-ecu-native — publish a native custom DDS type (libsils_vecu, P4b)

The same brake ECU as [`../brake-ecu`](../brake-ecu/), but it puts a **native typed
message on the wire** (`BrakeCmd { double force; unsigned long long seq; }`) instead of
the VISS envelope. This is the point of the `IWireCodec` port: a vECU can speak whatever
DDS type the real contract registers, by implementing one small codec — **no change to
control logic, plant, `RunProbe`, config, or the trace contract**.

## What differs from ../brake-ecu

| | ../brake-ecu | brake-ecu-native |
|---|---|---|
| behavior / plant | `BrakeBehavior` / `BrakePlant` | **same (reused verbatim)** |
| wire type | `VissRequestTopic` (string payload, VISS envelope) | **`BrakeCmd`** (typed fields) |
| codec | built-in `VissWireCodec` (default) | **`BrakeCmdWireCodec`** (`src/brake_cmd_wire.hpp`) |
| the ECU's `main` | `RunProbe(cfg, behavior, plant)` | `RunProbe(cfg, behavior, plant, make_unique<BrakeCmdWireCodec>())` |
| IDL | (none of its own) | `idl/BrakeCmd.idl`, generated by **this example's** CMake |

`diff ../brake-ecu/src/main.cc src/main.cc` — the injected wire codec is the only
functional difference. The behavior hands `RunProbe` an output each tick; the codec maps
`out.value → BrakeCmd.force` and `tick_seq → BrakeCmd.seq`.

## Bring your own IDL

`idl/BrakeCmd.idl` is **not** added to the core `idl/dds/` tree. This example's
`CMakeLists.txt` runs `fastddsgen` on it directly (at configure time) — exactly what an
out-of-tree developer does in their own repo. So a new native type needs no core change
and doesn't appear in non-SILS builds.

## Build & run

Built by any SiLS build (`SILS_BUILD_EXAMPLES=ON`), producing `bin/brake_ecu_native`:

```bash
./build.sh --build-sils
SILS_CTRL_KP=4.0 SILS_CTRL_SETPOINT=5.0 SILS_PLANT_INIT=30.0 \
VISS_DDS_DOMAIN_ID=42  <output>/bin/brake_ecu_native
```

The `wire_start` trace shows `"name":"brake-cmd-native","type":"BrakeCmd"`; `plant_step`
traces are identical to the code-path brake ECU (speed 30→setpoint). A subscriber on the
topic now receives a typed `BrakeCmd`, not a JSON string.

## Known remaining coupling

`run_loop.hpp`'s optional response/input readers (reqresp / input-staging modes) still
reference `VissRequestTopic`, so this ECU still *compiles* the core VISS generated
sources even though it never publishes that type. Fully decoupling the read path (a codec
that also owns response/input decoding) is future work; the publish path — the headline
of "custom wire type" — is fully native here.
